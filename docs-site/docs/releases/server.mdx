# Server and dashboard release notes

Release notes for the server image, tagged `codemagic-patch-server-vX`. The
dashboard is included in the image and has no separate version. Every entry
starts with **Upgrade impact**: migrations, configuration changes, and anything
that restarts or replaces a service. Review it before upgrading. Managed Patch
runs the latest server; self-host operators upgrade with
[`cmpatch selfhost upgrade`](/docs/reference/cli-reference#self-hosting). The
other surfaces' releases are on the
[Release Notes](/docs/releases) page.

Reference: [Configuration](/docs/reference/configuration) ·
[Operations](/docs/reference/operations) ·
[GitHub releases](https://github.com/codemagic-ci-cd/codemagic-patch/releases?q=codemagic-patch-server)

## 0.10.0 {#v0-10-0}

*17th November 2026*

### Upgrade impact

- **Update `cmpatch` first:** Upgrade with
  [CLI 0.10.0](/docs/releases/cli#v0-10-0) or later. CLI 0.9.0 and older
  leave the server's checkout on the default branch, and this release's
  upgrade script refuses a checkout that is not at a release tag. A refused
  upgrade changes nothing. Update the CLI and run it again.
- **Image:** The upgrade checks out the `codemagic-patch-server-v0.10.0` tag
  and pulls `ghcr.io/codemagic-ci-cd/codemagic-patch-server:0.10.0` instead
  of building, so the server must reach `ghcr.io`. `--build-from-source`
  builds on the server as before.
- **Caddy:** The stack runs the stock `caddy:2-alpine` image, pinned by
  digest, and the server image serves the dashboard. `/worker/*` answers 404
  instead of the dashboard page, and a plain-HTTP install no longer sends an
  HSTS header.
- **Migrations:** `0021_credential_generation` adds one integer column each
  to `user_account`, `api_token`, and `oauth_session`.
  `0022_service_account_owner_team` adds `user_account.owner_team_id` and
  marks a `member provision` account as a service account of its team when
  it has never signed in and belongs to that team only. Existing tokens and
  sessions stay valid.
- **Sessions:** A session older than 90 days fails at its next refresh. Sign
  in again.
- **API tokens:** CI that creates tokens, adds or invites members, changes
  roles, or transfers apps with an API token stops working. See
  [API tokens](#v0-10-0-api-tokens).
- **Rollback:** Do not switch back to an older image alone once the database
  is migrated. If the upgrade fails after the stack is recreated, follow the
  steps the command prints, which end with restoring the pre-upgrade backup.
  See [Upgrades](/docs/setup/ongoing-maintenance#upgrades).

### Breaking: API tokens cannot create credentials or grant access {#v0-10-0-api-tokens}

An API token (`cm_pat_…`) can no longer give access to anyone else, so a
leaked token cannot leave access behind after it is deleted. These need a
browser sign-in (the dashboard, or `cmpatch login` without `--token`) and
answer a token with `403`, reason `session_required`:

- `token create`, and approving a CLI login
- `member add`, `member invite`, `member update`
- `member provision`, `member rotate-token`
- `app transfer`

A token can still manage apps, deployments, and releases, and remove
members, invitations, and tokens.

- **Logging:** The server logs each refused request with the token's ID.
- **Earlier grants:** Roles and invitations a token granted before this
  release are not revoked. If a token may have leaked, review your team's
  members.
- **First provider sign-in:** An account that has never
  signed in through a provider loses its API tokens at its first provider
  sign-in. This covers `member provision` accounts, and accounts created
  before OAuth sign-in that are linked by email. Create new tokens after
  that sign-in.

See [API tokens](/docs/using-patch/security#api-tokens-ci-and-automation).

### Sessions

- **90-day limit:** A sign-in ends 90 days after the provider sign-in,
  however often it refreshes. A CLI sign-in approved from the dashboard
  shares that dashboard sign-in's deadline.
- **Sign out everywhere:** The dashboard's API tokens page can now end every
  session on your account, including the current browser and every CLI, and
  delete all your API tokens. Use it when a token or device may be
  compromised. See
  [Sessions and signing out everywhere](/docs/using-patch/security#sessions-and-signing-out-everywhere).

### Service accounts

- **Owned by one team:** A `member provision` account is a service account
  of the team that created it. It has access in that team only, even if it
  is added to another team. The Members page marks it with a
  **Service account** badge.
- **Token rotation:** An admin of the owning team replaces the token with
  **Rotate token** on the Members page or
  [`cmpatch member rotate-token`](/docs/releases/cli#v0-10-0). The old token
  stops working immediately.

### Self-hosting

- **Published image:** Each server release publishes one image for x86 and
  ARM, with a build provenance attestation.
  [CLI 0.10.0](/docs/releases/cli#v0-10-0) installs and upgrades from it
  instead of building on the server.
- **Schema guard:** The server refuses to start on a database that has
  applied a migration the release does not know.
  `cmpatch selfhost upgrade` checks for that before it changes anything.

### Metrics API

Metrics responses now include values the dashboard used to calculate itself.
Existing fields are unchanged.

- **`success_rate`** on every metrics object: applied over applied plus
  failed, from 0 to 1, or `null` when both are 0.
- **`summary`** on deployment metrics and timeseries responses: the totals of
  the returned page or range, and the active devices of the last complete
  UTC day.
- **`cumulative_success`** on each timeseries series: the running Applied
  total per day.

### Dashboard

- **Metrics pages removed:** A deployment page shows adoption over time and
  the totals of the selected range; a release page shows its counters and
  the failure drill-down. Old `/metrics` links answer 404.
- **Who changed a release:** The release page shows who created and last
  updated the release, what they did, and when. Job attempts and failure
  detail appear only while a job runs or after it fails.
- **Live release history:** The deployment page refreshes its release
  history while a release is processing.
- **Sign-in buttons:** Each provider's button shows its logo.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.10.0).

## 0.9.0 {#v0-9-0}

*3rd November 2026*

### Upgrade impact

- **Migration:** The upgrade runs migration `0020_server_instance`, which
  creates the empty `server_instance` table that holds the usage report's
  instance id. No existing table is touched and no lock of note is taken.
- **Usage report, on by default:** Once a day, the server now sends Codemagic
  an anonymous usage report of aggregate counts. Codemagic uses it only for
  public statistics, never to enforce the licence's 1M MAU limit. Set
  `SERVER_TELEMETRY=false` (or `DO_NOT_TRACK=1`) in `.env.selfhost` to turn
  it off.
- **Configuration:** `docker-compose.selfhost.yml` now passes
  `SERVER_TELEMETRY`, `DO_NOT_TRACK`, and `SERVER_UPDATE_CHECK` through to
  the server. A `SERVER_UPDATE_CHECK=false` line in `.env.selfhost` was
  silently dropped before; it now turns the GitHub release lookup off as
  documented.
- **Rollback:** Safe. An older image ignores the `server_instance` table.

### Dashboard

- **Chart colours:** The deployment charts use muted series colours instead
  of neon ones, in light and dark mode.
- **Silo on the Status page:** The Status page names the bundled object store
  Silo, which is what runs. The health check path is unchanged.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.9.0).

## 0.8.0 {#v0-8-0}

*28th October 2026*

### Upgrade impact

- **Migration:** The upgrade runs migration
  `0019_metricEventDailyAggregates`, which adds the daily aggregate tables and
  the fold watermark, and builds an index on `metric_event (emitted_at)`.
  Metrics ingest waits for the index build, which takes longer on a large
  history. Reads are not blocked.
- **First fold:** Shortly after startup, the server folds the existing history
  outside the raw retention window and deletes those raw events, including
  individual failure details. On a large history, expect one long transaction
  per folded day on the first run.
- **Disk:** Postgres keeps the space the fold frees for new rows instead of
  returning it to the operating system, so the volume stops growing but does
  not shrink. To shrink it, see [Disk size](/docs/setup/ongoing-maintenance#disk-growth).
- **Rollback:** A server older than 0.8.0 reads raw rows only, so the days
  already folded disappear from its metrics. Restore the pre-upgrade backup
  instead of only switching back to an older image.
- No configuration change.

### Metrics: 8-day raw retention

- **Raw events kept 8 days:** Metric events older than 8 UTC days are folded
  once a day into daily aggregates, which are kept indefinitely. Counters, adoption
  charts, timeseries, and failure reasons are unchanged across the fold. The
  per-event failure list (`failure-events` in the CLIs, the failure dialog's
  event list in the dashboard) covers the retained days only, and a later
  `Applied` clears a device's earlier `Failed` events only within that window.
- **Ingest window:** An event dated 8 or more days before the day the server
  receives it, or more than 24 hours ahead, is acknowledged but not stored.
  SDKs already drop events older than 7 days, so devices with a correct clock
  are unaffected.

### Self-hosting

- **Install through ngrok:** The self-host scripts now support a local stack
  reached at an ngrok `https://` address through
  [`cmpatch selfhost install --ngrok`](/docs/releases/cli#v0-8-0).
- **Status page:** The upgrade hint now says to run `cmpatch selfhost upgrade`
  from the machine you installed from, which covers Fly installs as well as
  SSH ones.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.8.0).

## 0.7.0 {#v0-7-0}

*19th October 2026*

### Upgrade impact

- **Migration:** The upgrade runs migration
  `0018_drop_metric_event_sdk_version`, which drops the unused `sdk_version`
  column from the `metric_event` table. The lock it takes is brief and the
  table is not rewritten. Older SDKs that still send `sdk_version` keep
  working; the server ignores the field.
- **Rollback:** A server older than 0.7.0 still writes `sdk_version`, so after
  this migration its metrics ingest fails. Restore the pre-upgrade backup
  instead of only switching back to an older image.
- No configuration change.

### Fixes

- **Deployment and release pages:** The pages now fetch only the selected
  adoption chart range instead of all four. This reduces database load, and
  the pages no longer stall under heavy usage.
- **Backups:** A backup now restarts the exact server container it stopped.
  Before, the restart could start a server with a different image or
  configuration if either changed during the backup, as happens during
  `cmpatch selfhost upgrade`.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.7.0).

## 0.6.0 {#v0-6-0}

*6th October 2026*

### Upgrade impact

- **Migration:** The upgrade runs migration `0017_app_framework`, which adds a
  `framework` column to the `app` table with the default `react-native`. No
  index is rebuilt.
- **Error responses:** Problem details now include a machine-readable
  `reason`, and `detail` no longer names a `cmpatch` command. CLI 0.6.0 and
  `cmpatch-capacitor` print the remedy themselves. Update scripts that matched
  the old `detail` text.
- No configuration change.

### Capacitor apps

The server now stores each app's framework (`react-native` or `capacitor`);
`cmpatch-capacitor` sets it on `app create`. `GET /v1/teams/:id/apps` accepts
`framework=` and returns only apps with that framework; without it, all apps
are returned. Apps created before this release are treated as React Native.

The dashboard now shows commands for the app's framework. For a Capacitor app,
the New release dialog takes the built web assets (the `webDir` of
`capacitor.config`, or a ZIP of its contents), requires a target binary
version, and shows the `cmpatch-capacitor release` command instead of
`cmpatch release-react`.

### Binary version filter

The deployment page now has a **Binary version** menu that filters the
Adoption card and the release history table. It lists the versions that
reported in the selected range, plus group rows such as `1.x` and `1.0.x` when
a group covers two or more versions. The Metrics page has the same menu, and
the Active devices card counts the selected version or group. Release detail
now has a **By binary version** table with Downloaded, Ready, Applied, Failed,
and success rate per reported binary version, shown when two or more versions
reported.

- **API:** `GET /v1/metrics/deployments/:id/timeseries` and
  `GET /v1/deployments/:id/releases` accept `binary_version` (exact) or
  `binary_version_prefix` (dot-separated digits; `1` matches `1.0.0` and
  `1.10.2`, not `10.0.0`). Both together return `400 invalid_combination`.
  The timeseries response includes `binary_versions`.
  `GET /v1/metrics/releases/:releaseId` now returns `{ binary_versions, release }`.
- **Release history filtering:** A release matches when its explicit target
  binary version matches or any version in its current resolved target set
  matches, so fingerprint-expanded targets are included and superseded
  generations are not. Rollback gating and the suggested target for a new
  release use the unfiltered history.

### Full and diff download metrics

Release detail now has a card with the size and download count of the full
bundle and of the diff from the previous release. The diff size is measured
against the previous release only, so it is approximate when devices skip
releases.

See the [configuration reference](/docs/reference/configuration) and
[server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.6.0).

## 0.5.1 {#v0-5-1}

*2nd October 2026*

### Upgrade impact

- **Object storage image:** The bundled MinIO images are no longer available
  to pull, so the stack now uses PGSTY Silo images. The upgrade replaces the
  storage container; existing storage volumes stay compatible and need no data
  migration.
- No database migration or configuration change.

### Fixes

- **Backups:** A backup now restarts only the server service. Dependent
  services such as object storage or the database are no longer recreated
  before the backup is confirmed.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.5.1).

## 0.5.0 {#v0-5-0}

*23rd September 2026*

### Upgrade impact

- **Migration:** The upgrade runs migration
  `0016_metric_event_lifecycle_names`, which rebuilds an index on the
  `metric_event` table while holding an exclusive lock on it. On servers with a
  large metrics history, the upgrade takes longer.
- **Lifecycle names:** The server stores events from SDK 0.4.x and earlier
  under the new `Ready` and `Applied` names. Existing data is kept as is, and
  the metrics API response keys (`installed`, `success`) are unchanged. SDK
  0.5.0 needs this server; see
  [compatibility](/docs/releases#upgrade-order-and-compatibility).
- **New optional setting:** `GITLAB_OAUTH_BASE_URL`, for GitLab sign-in on a
  self-managed instance. Leaving it unset changes nothing.

### GitLab sign-in

Self-hosted servers can now use GitLab for sign-in, on gitlab.com or a
self-managed instance set with `GITLAB_OAUTH_BASE_URL`. GitLab accounts that
have only a confirmed primary email can sign in, and the sign-in button shows
the GitLab name and icon.

### Command palette and navigation

Added a command palette (⌘K / Ctrl+K) that opens apps, releases, metrics, and
teams, and runs common actions. The deployment page now shows update adoption
and links to the Metrics screens, and the sidebar lists apps with their
deployments. Release details now include a cumulative `Applied` chart of update
adoption over time.

- **Dashboard fixes:** Fixed page scrolling and removed blank space that a
  hidden chart table added at the bottom of the page. Cleaned up how the
  deployment and release detail pages show status, metrics, charts, and history.

See the [configuration reference](/docs/reference/configuration) and
[server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.5.0).

## 0.4.0 {#v0-4-0}

*14th September 2026*

### Upgrade impact

- **New optional setting:** `S3_INTERNAL_BUCKET`, described below. Leaving it
  unset keeps single-bucket routing.
- No database migration.

### Changes

- **Private storage:** S3-compatible storage can use `S3_INTERNAL_BUCKET` to
  keep internal uploads and worker artifacts in a separate private bucket while
  release artifacts are served publicly. Leaving it unset keeps single-bucket
  routing.
- **Dashboard appearance:** Added light, dark, and system themes, refreshed
  branding, and improved accessibility. Fixed translucent callouts in dark mode.
- **Delivery metrics:** Release details no longer show Active counts.
  Deployment summaries show successful installs, and release history includes
  downloads. Success counts are installations, not users currently running a
  version.
- **Localhost HTTP:** Run `scripts/selfhost/install.sh --allow-http` from a local
  clone to test the self-hosted stack without TLS certificates or public DNS.
  Service ports bind to loopback; OAuth setup is still required.

See the [configuration reference](/docs/reference/configuration) and
[server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.4.0).

## 0.3.0 {#v0-3-0}

*7th September 2026*

### Upgrade impact

- **Migrations:** `0013_metric_event_failure_payload` adds the nullable
  `failure_payload` column to `metric_event`, without backfilling existing
  events. `0014_metric_event_failure_feed` and
  `0015_metric_event_device_outcome` create three indexes on that table for
  failure details and device outcomes. Index creation is not concurrent and
  blocks writes to the table; allow extra upgrade time on servers with a large
  metrics history.
- **Cloudflare users:** After you upgrade, delete the two-hour Edge TTL Cache
  Rule for `.json` from the previous setup guide, and remove any
  `MANIFEST_CACHE_CONTROL` line from `.env.selfhost`. The Cache Rule overrides
  the origin `s-maxage` and extends the stale window from five minutes to two
  hours. A leftover `MANIFEST_CACHE_CONTROL` pins the old `no-cache` value, so
  manifests are never cached at the edge. See
  [CDN settings](/docs/reference/cdn#add-cache-rules).
- No configuration change beyond the Cloudflare cleanup.

### CloudFront delivery

Devices can now fetch artifacts from Amazon CloudFront, in addition to
Cloudflare or the origin host, for bundled MinIO or external S3/GCS. The
install wizard prints the AWS Console values, generates the origin secret, and
verifies the distribution before you move DNS. It does not create AWS resources
or ask for AWS credentials beyond the scoped purge key. See
[CDN settings](/docs/reference/cdn#cloudfront).

### Failure details

Failed installs reported by [SDK 0.3.0](/docs/releases/react-native#v0-3-0)
include diagnostic details: HTTP status, the origin or platform error message,
and on Android 11+ the previous process exit reason. Previously the dashboard
showed only a `network` count. On the metrics view, open a failure reason to
see its codes, then open a code to see the values behind it. See
[Analytics and metrics](/docs/using-patch/analytics).

### Failure counts exclude later successes

Failure counts now include only devices that never got the update, not network
retries that later succeeded. When a device later installs the same package
successfully, its earlier `Failed` events for that package are dropped. A late
`Failed` after an `Applied` is acknowledged and discarded.

### Status page

The dashboard has a new **Status** page. It shows API and database health,
whether the download URL is reachable, disk use on a bundled single-host
install, and the running server version compared with the latest GitHub
release. The disk and version cards are hidden on topologies where they do not
apply.

See the [server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.3.0).

## 0.2.0 {#v0-2-0}

*25th August 2026*

### Upgrade impact

- **Fingerprint checks:** Uploads from CLI 0.2.0 and the dashboard are
  rejected with `409` when the fingerprint disagrees with the one recorded for
  the deployment and binary version, unless the client overrides it. Older
  clients keep the warning-only behavior.
- **New optional setup:** Compose can target an external PostgreSQL database
  and S3-compatible bucket (see below). The default install is unchanged.

### Fingerprint mismatch check

Uploads can now send `block_on_fingerprint_mismatch: true`. When the release
fingerprint differs from the value already recorded for that deployment and
binary version, the server returns `409` and creates no release. The dashboard
compares fingerprints the same way and shows the details before you proceed.
CLI 0.2.0 and the dashboard send the flag by default; older clients and
explicit overrides keep the previous warning-only behavior. See
[Fingerprinting](/docs/using-patch/fingerprinting).

### Failure reasons

Metrics APIs and the dashboard now expose `failure_reasons` on each release,
which break failures down by category: integrity, signature, rollout, or
another category. The counts sum to `failed`. See
[Analytics and metrics](/docs/using-patch/analytics).

### External Postgres and object storage

Compose can now use a managed PostgreSQL database and an S3-compatible bucket
instead of the bundled Postgres and MinIO containers. The default
`scripts/selfhost/install.sh` run still creates the bundled stack. For an
external database or storage, pass the install script's database and storage
flags, then configure adapters as described in
[Infrastructure](/docs/setup/infrastructure) and
[Configuration reference](/docs/reference/configuration).

Backup and restore depend on the deployment mode: the default backup script
does not copy external databases or buckets. Use provider-level backups for
those components. See [Operations](/docs/reference/operations) and the
[server release](https://github.com/codemagic-ci-cd/codemagic-patch/releases/tag/codemagic-patch-server-v0.2.0).
