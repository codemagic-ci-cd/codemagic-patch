# Fingerprinting

A fingerprint is a hash of the native code in your project. Patch computes it at release time and records the first value it sees for each deployment and binary version.

It is a compatibility signal. Matching fingerprints should mean compatible native code but are not a 100% guarantee.

## What goes into it

The hash covers the native side of your project, not your JavaScript. For a bare React Native project the inputs include:

- The `ios` and `android` directories.
- Your `.gitignore`, hashed as a file in its own right.
- Autolinked native dependencies, resolved from `node_modules`.
- The `react-native` package version, and the `scripts` block of `package.json`.

Three consequences are worth knowing before wiring a release into CI.

**Committed lockfiles count; generated output usually does not.** `ios/Podfile.lock` is an input, so it is part of the hash. `ios/Pods/` is not, because `@expo/fingerprint` ignores `**/ios/Pods/**/*` by default, so running `pod install` does not move the fingerprint. Commit `Podfile.lock` and have CI install from it. If CI regenerates the lockfile instead, the fingerprint changes and the next release is blocked as a disagreement.

**Editing `.gitignore` changes the fingerprint**, even when no native code changed, because the file itself is hashed.

**`.gitignore` does not decide what gets hashed.** A file under `ios/` or `android/` still counts even when git ignores it. To exclude paths from the fingerprint, use [`.fingerprintignore`](https://docs.expo.dev/versions/latest/sdk/fingerprint/#fingerprintignore).

Measured on a bare React Native project, changing one thing at a time:

```text
baseline                            1c7f0558ebe8a7ad903b5de34b2faf49b10dab3b
ios/Podfile.lock removed            14f7cb0ffcd3a39fbfa86d400aa319c7d2348656   changed
ios/Pods/ present                   1c7f0558ebe8a7ad903b5de34b2faf49b10dab3b   unchanged
.gitignore edited                   6a0a7df7936d6f914c95002bbd4b056ccc5543f2   changed
  then a file it ignores created    a7fcb5d623a44e4366b57bd19db194b02b3eaea1   changed again
```

The last pair is the one to notice: adding `ios/ScratchDir/` to `.gitignore` changed the hash, and then creating `ios/ScratchDir/file.txt` changed it again. Being ignored by git did not keep the file out of the fingerprint.

## How it helps

### Disagreements

If a new release's fingerprint disagrees with the value already stored for that binary version, the current CLI and dashboard block the publication. The block is designed to stop accidental incompatibilities, and you can override it once you have checked that the release targets the intended native binary:

- In a terminal, `cmpatch release-react` and `cmpatch release create` show the stored and release fingerprints and ask you to confirm before they retry.
- In CI, or with `--yes`, there is no prompt: the command fails with a hint. Pass `--allow-fingerprint-mismatch` to publish anyway.


### Expansion

The SDK usually only installs a release whose target binary version matches the running app. Fingerprint expansion is the exception: the worker also publishes that release to other binary versions that already recorded the same fingerprint.

Store builds that share native code can therefore receive the same OTA without you targeting each binary version by hand.


## Register each store build

Fingerprint checks rely on having a baseline for that binary version for further releases to check against.

On each store (or production-track) build, from the same commit as the published binary, create a disabled release on the deployment those devices use:

```bash
cmpatch release-react \
  --platform ios \
  --deployment Production \
  --disabled \
  --yes
```

Using `--disabled` means the release is stored on the server and the fingerprint is recorded, but devices do not download it. Later OTA releases to that binary can then be checked against the fingerprint.

For targeting and promotion, see [Releasing updates](/docs/using-patch/releasing-updates).
